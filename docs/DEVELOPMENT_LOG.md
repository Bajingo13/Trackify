| Address precision | Place search asked Nominatim for `addressdetails=0`, so a result arrived as one display string with no street, barangay or house number in it — a city-centre pin and a street address looked identical in the picker and both dropped a pin. Search now returns address components, a precision rung (house, street, barangay, city, province, area), a Philippine-ordered label, and honours a local viewbox so a common street name stops resolving to the same-named street across the country. Structured search (house, street, barangay, city) and reverse geocoding were added; a dropped pin previously recorded its own coordinates as the trip's origin. | Proven against a running API: free text near Davao returns street-level hits with real barangays, reverse geocoding on a Davao point returns "E. Calls are queued 1.1s apart with a 10-minute cache, because Nominatim's policy is roughly one request per second and the penalty is the deployment's IP being blocked. |
| Two wrong diagnoses, recorded | A structured search for "123 Rizal Street, Digos City" returned nothing and I blamed first the redundant `country` parameter and then folding the barangay into Nominatim's `city` field. | Structured trip address | A trip's origin and destination were each a single VARCHAR(200), so the street and barangay the geocoder now finds had nowhere to live: everything flattened back to one label and the system could route a truck exactly while being unable to answer which barangays it delivered to. Migration 028 adds house number, street, barangay, city, province and postcode for both ends, indexed on (company_id, barangay) since that is the level a dispatcher groups a day's drops by. Flat columns rather than a joined table — there are exactly two addresses per trip, every list and report query already reads the row, and a join would be paid on all of them to normalise data no two trips share. | Done and round-tripped against live data: a create wrote each part into its own column, an edit that never mentioned the address preserved it, and an edit that changed it wrote the new barangay without touching the destination. No new input boxes — the picker already returns the parts with every search hit and every dropped pin, so searching or pinning carries them along. Existing trips keep null parts; nothing rewrites history. |
