New capability

Feature

Drivers log expenses from the road, with a receipt photo

A driver files fuel, tolls, parking and the rest against a trip assigned to them, attaching a photo straight from the phone camera. Claims arrive as submitted and sit in a review queue where finance sees the receipt beside the amount, the driver's name and the trip.

Approving is what makes a claim recorded, and only a recorded expense can reach a voucher — so nothing a driver types posts to the books unreviewed. Rejection requires a reason, which the driver sees in their app.

Before Expenses were typed in second-hand from a paper receipt by office staff. The driver was never in the loop, and the system had no file storage at all.

Feature

Proof of delivery is a record, not a sentence

Confirming a delivery now captures who signed for the load, an optional note, a photo, and the position and time the driver captured it — read when the sheet opens, so it reflects the drop-off rather than wherever the phone ends up. One POD per trip is enforced by a database key, not just by the handler.

Before A window.prompt asking for a name, stored as the words "POD — received by …" in the trip's status history. No photo, no location, no record.

Feature

The driver app survives a dead zone, and installs

Work filed without signal is parked on the phone and replayed in order when coverage returns; a banner tells the driver exactly what is saved and unsent. Stale GPS positions expire rather than replaying a trail the truck already finished driving. The app now carries a manifest, icons and a service worker, so it installs to a home screen and opens offline.

Before No offline handling of any kind. Every ping, expense and delivery filed out of coverage was lost silently, and the app looked identical online and off.

Feature

Light and dark theme

A three-way switch — light, dark, or follow the operating system — applied before the first paint so there is no flash of the wrong theme.

Corrections — things that were wrong

Fixed

Two panels reported figures that could never be true

Delivery Performance read a hard-coded zero stub while the dashboard was already passing it real values, so it showed a permanent 0% and "0 / 0" alongside an invented "↑ 0% vs previous period". It now uses the real on-time rate, and shows an em dash when nothing has closed rather than a zero that reads as failure. POD Completion was removed: no proof-of-delivery data existed at the time, so the figure was fiction.

Fixed

Every page load fired a forbidden request

The notification bell asked for exceptions regardless of permission — for a warehouse officer that was a rejected request on all 38 routes, on every navigation. The same pattern sat in the dashboard summary, the operations report, the admin user screen and live tracking. Five call sites now check permission before asking.

Fixed

Trips with no coordinates could never show distance or time

Seven trips had been saved without coordinates, so no route could ever be computed for them and Distance and Estimated time stayed blank forever. The trip form now geocodes typed place names on save, and a backfill script filled the existing ones. All 27 trips now carry a computed route.

Fixed

An offline expense could be filed twice

Found by the new offline test: two replay attempts starting at once — the reconnect event and a startup check — read the same queued rows before either removed one, filing the driver's expense twice. Replay now holds a single in-flight lock.

Fixed

Form controls and Cancel buttons vanished in dark mode

Twelve copies of one hard-coded input style across Fleet and Warehouse painted every field pale with no text colour set, so status and type filters became unreadable. Cancel buttons had the same fault in two variants. All now use the theme tokens.

Fixed

A rejected expense claim could not be cleared

Deletion allowed only recorded expenses and refused everything else with a message about vouchers — which blocked a rejected claim that never reached the books. A claim awaiting review must now be decided first; a rejected one can be removed.

Fixed

Nine drivers could not sign in

All ten demo drivers had PINs, but app access had been switched on for only the first, from a time when the driver app was read-only tracking. The drivers actually carrying trips can now sign in. A delivered trip also stays visible for three days instead of one, so receipts can still be filed after a late arrival — and the expense endpoint enforces the same window, where before it accepted any delivered trip however old.

Interface

Improved

Dashboard rebuilt around what needs a decision

Four tall cards became one metric strip, freeing the room for a working row: trip activity, the on-time rate, vehicles on the road, and the run worth watching with its real milestones. A step with no actual timestamp is drawn hollow and marked planned.

Improved

Live Tracking and Dispatch became working screens

Both now fill the viewport with independently scrolling panels. Live Tracking gained a detail panel with tabs, a load-capacity view and driver contact; Dispatch opens with the yard's real spare capacity and lists people one scannable row each instead of one card per person.

Improved

Vehicles are drawn by type, and move when they are moving

Ten distinct silhouettes replace one generic truck, chosen from the vehicle's own type field. Wheels turn and the road streaks past only where something is genuinely in transit — a parked unit sits still, which is what makes the motion mean anything.

Improved

One status pill across the whole Fleet module

Every fleet page had carried its own colour map, so the same status looked different from page to page and none survived dark mode. Colour is now reserved for interaction state and genuine warnings.

Removed

Dead code and placeholder records

An unrouted 1,300-line legacy trips page and the navigation only it used; four dashboard components that were never rendered and imported exports that no longer existed; and two placeholder trip tickets that could never be routed.

Still open

No rate limiting on sign-in

Neither the staff login nor the driver PIN throttles attempts. A four-digit PIN with unlimited guesses is the one item that should block real use.

Demo accounts are still live

Ten fully-permissioned demo logins and a known driver PIN must be disabled before the system faces real data.

Receipts and delivery photos have no backup

They sit on one local disk with no retention or offsite copy. Losing it loses the evidence behind approved claims and completed deliveries.

Nothing is deployed

No container, web server or hosting configuration exists; the system runs on a local machine. Session tokens are safe in the browser only behind HTTPS.

Integrations and Settings screens

Both still render a placeholder. Two of thirty-eight screens.

BIR / EIS handshake

A deliberate boundary — the client runs their own filing system. Completing it depends on their side, not this one.

No user acceptance testing

Every check so far is automated. No dispatcher or driver has used the system on real work.

Position. Feature development is substantially complete and system testing has passed. What remains before real use is operational rather than functional — hardening the way in, protecting the files, putting it somewhere, and letting real dispatchers try to break it.
