01 System overview

Trackify is a truck-trip management system for a Philippine logistics operator. It runs one company with several branches, and covers a trip from the moment it is requested until it is delivered, invoiced and closed on the books.

The product is a monorepo with two independent apps plus a phone app served from the same frontend:

frontend/Staff web app. React 19 + Vite. Runs on port 8443.
frontend/ → /driverDriver phone app. Same build, separate route tree, its own login.
backend/REST API. Node + Express 5, MySQL. Runs on port 5000 as plain node server.js.

Ground rules that shape everything below

  • One company, many branches. Almost every record carries a company_id and usually a branch_id. Users only see data inside their company, and role scope can further limit them to their branch.
  • RBAC everywhere. The menu, every page, and every API route are gated by named permissions (e.g. trip.assign). system.admin is a wildcard.
  • The backend does not auto-reload. After any backend code change it must be stopped and restarted by hand.
  • Dates are stored as plain dates (no timezone shifting) — the pool is configured with dateStrings for DATE columns.

Assignment / availability model (worth understanding for QA)

  • A trip keeps its assignment history. The row marked is_current means "the driver/vehicle that handled this trip" — it survives the trip ending, so a finished trip still shows who drove it.
  • A vehicle or driver counts as busy only while it has a trip whose status is assigned, accepted, released or in_transit. Once the trip is delivered/closed they are free again, even though the history stays.
  • Reassign works only before the trip has left (up to assigned). Swapping frees the previous vehicle/driver automatically. A trip that is in_transit can no longer be reassigned.

04 Live tracking — how it works

There is no paid GPS box in the trucks and no Google Maps key. Live tracking is assembled from the driver's phone plus three free OpenStreetMap-based services.

The four pieces

PieceWhat it isJob in Trackify
MapLibre GL JSOpen-source map rendering library (a fork of Mapbox GL). Draws the map on an HTML canvas and offloads tile decoding to a web worker.Renders the map on Live Tracking, the trip Route tab, and the driver's trip screen. Wrapped once in frontend/src/components/map/MapView.jsx.
OpenStreetMap tilesPre-rendered 256×256 PNG map images, addressed by zoom/x/y.The base map picture. Trackify uses an inline raster style pointing straight at tile.openstreetmap.org — no vector-tile pipeline, no key.
NominatimOpenStreetMap's geocoder: turns a typed place name into coordinates.The "search for a place" box in the trip location picker. Backend route GET /operations/geo/search, results biased to the Philippines.
OSRMOpen Source Routing Machine: given two points, returns the driving route, its distance, its duration and the road-following line geometry.Planned distance + ETA for a trip, and the blue route line on the map. Backend route POST /operations/geo/route.

  1. Driver signs in at /driver with employee number + PIN. This issues a separate JWT stamped kind:"driver" (12-hour expiry). That token can only touch /api/v1/driver/* routes — staff routes reject it, and driver routes reject a staff token.
  2. Driver opens a trip and turns on "Share my location." The browser asks for location permission. watchPosition then fires whenever the phone gets a new fix.
  3. The app throttles those fixes to one every ~20 seconds and POSTs {lat,lng} to /driver/trips/:id/ping. Pings are only accepted while the trip is released or in_transit.
  4. Each ping is stored as a row in trip_tracking_points.
  5. Live Tracking polls the API for active trips. For each it gets the latest point (current position), the stored planned route (blue line), and the full trail of points (where the truck has actually been).
  6. MapLibre draws it: a pulsing pin at the current position, the route line, and the breadcrumb trail. Selecting a trip flies the map to it.

Realtime updates (WebSocket)

Live Tracking no longer waits for a poll. The backend runs a WebSocket hub at /ws (same port as the API); the staff app opens one connection, scoped to the user's company and branch, and receives events the moment they happen:

  • trip:location — every GPS ping (from the driver app or a staff device) moves the truck pin and extends the trail immediately.
  • trip:status — assign, release, start, deliver, close, cancel — the board refreshes right away.

It is a one-way broadcast (server → clients); the client never sends anything over the socket. If the connection drops it reconnects on its own with backoff, and a 60-second poll still runs as a fallback — the header shows ● live when the socket is connected, ● polling when it isn't. Auth is the same staff JWT, passed as a query parameter; driver tokens are rejected.

Accuracy — how the line is kept honest

Earlier the map drew a straight line between origin and destination (there was no stored road path), and a demo trip to "Zamboanga City" carried mis-seeded coordinates pointing into the sea. Both are fixed:

  • The road path is computed once and cached on the trip (route_distance_km, route_duration_min, route_geometry). The map draws that stored polyline, so it always matches the shown distance/ETA and survives a slow or failed routing call. A simplified geometry is stored (≈15–60 points) — enough to trace the roads, small enough not to bloat the payload.
  • The GPS trail is snapped to the road network server-side (OSRM map-matching) before it's drawn, so the breadcrumb follows streets instead of cutting straight lines across bends and water. If matching fails it falls back to the raw line.
  • Wildly imprecise phone fixes are dropped. The driver app ignores any GPS reading with an accuracy worse than 150 m (cell-tower / wifi triangulation) so a bad fix can't yank the trail across the map.
  • Demo trip coordinates were corrected against a real gazetteer; destinations with no road route from Davao (Cebu, Manila) are left blank rather than pointed at a wrong place.

To push accuracy further: set ORS_API_KEY (OpenRouteService — the router tries it first, then falls back to the OSRM demo), or point OSRM_URL / NOMINATIM_URL at self-hosted instances for production traffic.

Known constraint: the free OSRM and Nominatim demo servers are rate-limited and occasionally slow (routing calls now time out after 8 s rather than hanging). If a trip's distance/ETA doesn't compute on save, retry or run npm run db:backfill-routes, or set ORS_API_KEY. The map picture (OSM tiles) is separate and much more reliable.

  1. Reports → Operations and Reports → Fleet.Figures reflect the trips and vehicles you touched above (trip counts, distances, service due).
  2. Audit Log → filter to today.Your create/assign/approve/post actions are listed with the acting user and timestamp.
  3. Dashboard → check the KPI cards and Active Trips / Fleet Availability widgets.Consistent with everything above — no placeholder numbers.

Cleanup after manual QA

Delete the QA test customer, its trips and any expense/voucher/invoice you created, and reset any vehicle service interval you changed, so the demo returns to its seed baseline.

Warehouse module — finished this pass

The warehouse backend (items, inventory, stock movements + receive/cancel, branch transfers full lifecycle, cargo release/return) was already solid — the 48-check QA pass confirmed it. Three gaps were closed: (1) releasing cargo now advances the trip to released (previously it only logged an event, and the warehouse officer — who has no trip.release permission — couldn't move the trip, so the driver was stuck); (2) a low-stock endpoint feeds a real Operational Alerts panel on the dashboard plus a clickable "Low Stock / Out of Stock" filter on the Inventory page; (3) npm run db:reset-demo restores the seed baseline after QA. Deliberately deferred: consuming maintenance parts from inventory (fleet-side, optional).

Bugs found and fixed during this pass

Driver token accepted on staff routes. A driver-app JWT (same signing secret, but kind:"driver" and no userId) passed the staff authenticate middleware, then blew up downstream with a 500 instead of being cleanly rejected. Fixed in backend/src/middleware/authenticate.js — staff auth now rejects any token that is kind:"driver" or lacks a userId with a 401. Re-verified: staff routes reject driver tokens, driver routes reject staff tokens.
Cross-branch assign was blocked, not warned. The redesigned Trips page (TripsPage.jsx) had lost the "warn but allow" handling — a cross-branch pick just threw a red toast and could never go through. Restored: the assign dialog now shows the amber "Different branch" note and an Assign anyway button that retries with allowCrossBranch: true. Same pass also restored two things the redesign had dropped: the Set on map location picker on the trip form (without it, new trips got no coordinates → no route, distance or live tracking) and the Route tab map with planned distance / ETA on the trip detail.
Live Tracking route line cut through water. No road path was stored (the map drew a straight origin→destination line), and migration 015 had seeded wrong coordinates for several demo destinations. Fixed: migration 017 adds route_geometry and corrects the seeded coordinates; scripts/backfillRoutes.js computes and caches a real (simplified) road path per trip; the GPS trail is now road-snapped; the driver app drops low-accuracy fixes; the router tries ORS then OSRM with an 8 s timeout. See section 4.
Test data: all QA fixtures created this pass were removed afterwards — the QA vehicles, the generated trips and their downstream records, the "E2E Customer ZZ" chain, and the QA finance documents (vouchers, invoices, journal entries) — leaving the database at its seed baseline (29 trips, 5 customers, 10 vehicles, 1 seed voucher / invoice / journal entry). A few pre-existing hand-made test trips ("asdasd", "A → B", "Balayan → Makati") were left untouched as they predate this work.
